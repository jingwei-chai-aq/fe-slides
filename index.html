React · virtual DOM

Why the virtual DOM — cheap redraws

Touching the real DOM is the expensive part. Old-school code hits it constantly; React hits it as little as possible.

React · JSX

What is JSX?

HTML-like syntax inside JavaScript. It isn't HTML — the bundler compiles every tag into React.createElement, which builds a virtual-DOM node.

you write JSX

<td>{pnl}</td>

→

the bundler compiles it to JS

React.createElement('td', null, pnl)

→

React builds

a vDOM node

It's JS, not HTML

className not class, onClick not onclick — class and for are reserved words.

Every tag closes, one root

Self-close <br />. An expression yields one value, so return a single root — wrap siblings in a fragment <>…</>.

Mental model: the extension tells you the language — .jsx is JS with tags, .tsx is TypeScript with tags. All our components are .tsx: typed, plus JSX.
React · components

Anatomy of a component

A component is just a function — logic at the top, and whatever it returns is the UI. Use it like a tag; a big screen is a tree of them.

PositionRow.tsx
function PositionRow({ symbol, pnl }) {  // ① fn + ② name
  const color = pnl >= 0 ? 'green' : 'red';  // ③ logic

  return (                            // ④ return = UI
    <tr>
      <td>{symbol}</td>
      <td style={{ color }}>{pnl}</td>
    </tr>
  );
}

① A function

A component is declared with the function keyword (or an arrow fn).

② A CamelCase name

Must start uppercase — PositionRow, not positionRow. That's how React tells a component from a plain HTML tag.

③ Body = logic

Variables, hooks, helpers — the plain JS that runs each render, before the return.

④ return is the UI

Whatever JSX it returns is what shows on screen — one root element.

React · useState

Why useState? — a plain variable won't redraw

A component re-runs top to bottom every render, so a plain let resets — and reassigning it never tells React anything. State is the memory React keeps; its setter is what schedules the redraw.

❌ Screen stays 3
plain variable
function Counter() {
  let a = 3;
  const onClick = () => {
    a = 5;   // React never knows
  };
  // a changed, but no re-render
  // is scheduled — screen frozen
}
✅ Screen updates to 5
useState
function Counter() {
  const [a, setA] = useState(3);
  const onClick = () => {
    setA(5);   // schedules re-render
  };
  // stores value AND re-runs the
  // function → UI redraws with 5
}
Mental model: changing data is not enough — only a state setter triggers a re-render. If the screen should change, it must be state.
React · useState

useState — the updater function

State is a snapshot per render and updates are batched — so three +1 calls that read the bare value all read the same start and land on +1, not +3.

❌ stale — reads a snapshot
// count is 0 this render
setCount(count + 1);
setCount(count + 1);
setCount(count + 1);
// all read 0 → count = 1

// React batches these;
// count is frozen per render
✅ updater — reads the latest
setCount((prev) => prev + 1);
setCount((prev) => prev + 1);
setCount((prev) => prev + 1);
// chains → count = 3

// lazy init — runs once:
const [rows, setRows] =
  useState(() => parse(csv));
Gotcha: when the next state depends on the previous — counters, toggles, appending, accumulating ticks — use setX(prev => …), never setX(x + 1).
React · useEffect

useEffect — side effects

Rendering only computes markup. Anything touching the outside world — fetching, a WebSocket, a timer — is a side effect and lives in useEffect. The returned function is the cleanup.

ticker.tsx
useEffect(() => {
  const ws = connectTicker(symbol, setPrice);  // the effect
  return () => ws.close();                     // the cleanup
}, [symbol]);  // deps: re-run only when symbol changes
Dependency arrayWhen the effect runs
[]Once, after mount. Cleanup at unmount. For one-time setup
[symbol]After mount, and again whenever symbol changes (cleanup runs between)
omittedAfter every render — almost always a bug (exhaustive-deps catches it)
React · useEffect

useEffect — fetching from the network

Run the async call in the effect, store the result in state, re-run when the inputs change. Learn the shape to see what's under the hood — then reach for React Query.

fetch-in-effect.tsx
useEffect(() => {
  let active = true;                        // race guard
  setStatus('loading');
  fetchPositions(symbol)
    .then((data) => { if (active) setRows(data); })   // ignore if stale
    .catch(() => { if (active) setStatus('error'); });
  return () => { active = false; };        // cleanup on change/unmount
}, [symbol]);                            // re-fetch when symbol changes
React · useRef

useRef — the mutable box

A ref is a mutable box (.current) React keeps for the component's life. Changing it does not re-render, and the value survives every render.

a DOM handle
const inputRef = useRef(null);

// focus it after mount
useEffect(() => {
  inputRef.current?.focus();
}, []);

<input ref={inputRef} />
a value that shouldn't re-render
const timer = useRef(null);

timer.current = setInterval(tick, 1000);
// ...later, to stop it:
clearInterval(timer.current);

// changing .current does
// NOT trigger a re-render
Mental model: if changing the value should update the screen → useState. If it's just bookkeeping the UI doesn't react to (timer ids, DOM nodes, socket handles, "already ran" flags) → useRef. Never touch .current during render — only in effects and handlers.
React · useMemo & useCallback

useMemo & useCallback — cache across renders

A component re-runs top to bottom every render, so every value and function it defines is rebuilt. These cache a computed value and a function's identity.

memo.tsx
// useMemo: filter + sort ONLY when rows or query change
const visible = useMemo(
  () => rows.filter((p) => p.symbol.includes(query))
            .sort((a, b) => b.pnl - a.pnl),
  [rows, query]
);

// useCallback: same identity, so a memo'd Row skips re-renders
const onPick = useCallback((symbol) => setSelected(symbol), []);
Gotcha: React 19 + the React Compiler auto-memoize at build time. Reach for these far less — only where the Profiler shows a real hot spot. Don't sprinkle them just in case.
React · hooks

The everyday hook kit

The rest of the kit — each hook doing one job. Custom hooks combine these and are the backbone of our MVVM.

useStateGive the component memory that survives re-renders
useEffectReach outside — fetch, subscribe, timers; return a cleanup
useRefA mutable box that survives renders without causing them — timers, DOM handles
useMemoRemember the result of an expensive calculation until its inputs change
useCallbackRemember a function itself, so it stays the "same" reference across renders
useContextRead a shared value provided higher up the tree
Rule of thumb: useMemo/useCallback are manual memoization. The React Compiler (React 19) auto-memoizes at build time — reach for them far less, only where the Profiler shows a real hot spot.

React · prop drilling

The prop drilling problem

The logged-in user lives in App; a tiny Avatar deep down needs it. Props only flow one hop at a time — so you thread it through every layer in between.

The parcel relay

App (has user)
 └─ Layout   ↓ user // unused
    └─ Header ↓ user // unused
       └─ Nav ↓ user // unused
          └─ Avatar ✓ uses user

Every layer in between grows a prop it doesn't care about.

The notice board

App provides user ┐
 └─ Layout       │
    └─ Header   │ context
       └─ Nav   │
          └─ Avatar reads ◄┘

Provide once at the top; read directly below — no couriers.

Mental model: prop drilling = relaying a parcel hand to hand through people who don't need it. Reach for Context when a value is needed in many far-apart places — 2–3 hops of plain props is fine.
React · Context

Global Context

Context is a notice board — pin the value once at the top of a subtree, and anyone below reads it directly with useContext. No courier props.

UserContext.tsx
const UserContext = createContext<User | null>(null);

// at the top of a subtree:
<UserContext.Provider value={user}> <Layout /> </UserContext.Provider>

// anywhere below — no courier props:
const user = useContext(UserContext);
In our stack: we manage global context with react-reservice — not raw Context — so components subscribe to just the slice they read (covered in Part 3).
React · Context

Why not just Context?

Everyone reaches for Context first — but every consumer re-renders on any change to the value.

useContext

A notice board

Publish a value once; any child reads it. But every consumer re-renders on any change.

Safe only for slow-changing state — session, theme, locale.

react-reservice

Subscribe to one slice

Subscribe to one slice of the store; re-render only when that slice changes.

A price feed ticking many times a second belongs here — not on the notice board.

Gotcha: reach for Context when a value rarely changes; a Service for anything that ticks. Put a live price feed in Context and you re-render the whole subtree on every tick.

aqx-core · apiViewController

apiViewController — the template for every API call

Every API call follows one shape: typed request and response schema in, onSuccess and onError out. Writes always go through the Service.

orderViewController.ts
const createOrder = (params: ICreateOrder) =>
  orderApi.create<ICreateOrder, IOrder>(params, {
    onSuccess: (res) => orderService.setLastOrder(res),
    onError:   (err) => snackbar.show(err.message),
  });

Typed both ways

Request and response are typed to the Model schema — the contract is enforced at the call site.

onSuccess + onError, always

Both callbacks are non-negotiable in review. Success saves; error is handled, never a crash.

Writes go through the Service

onSuccess only ever calls a Service setter — the ViewController never mutates state directly.

aqx-core · Service

Service — the source of truth

A Service holds state, setters and context — and nothing else. No API calls, no business rules: it is pure, observable memory, one per domain.

orderService.ts
class OrderService extends Service<{ lastOrder?: IOrder }> {
  setLastOrder(o: IOrder) {
    this.context.lastOrder = o;   // setter only, no logic
  }
}

export const orderService = new OrderService();

State + setters + context

The typed context is the observable state; setters are the only way to change it.

No business logic

No API calls, no rules. Anything that decides or transforms belongs in the ViewController.

Never called by UI

The View reads through a Hook and writes through a ViewController — it never touches the Service.

aqx-core · ViewController

ViewController — the brain

All business logic lives here. A class of methods the View calls — it applies rules, calls the API, and writes results into the Service. Real example: OrderViewController.

order/controller.ts
class OrderViewController {
  private selectedTab = Tab.OPEN;          // local logic state

  public fetchOrders = async () => {
    orderService.setLoading(true);        // write to Service
    await orderAPIController.getOrders(params, {
      onSuccess: (result) => {           // apply rules…
        orderService.setOrders(sortByOpenTime(result));
      },
      onError: () => snackbar.error('Load failed'),
      onFinally: () => orderService.setLoading(false),
    });
  };

  public selectOrder = (order) =>
    orderService.setSelectedOrder(order);
}
export const orderViewController = new OrderViewController();

A class of methods

Public methods are what the View calls (fetchOrders, selectOrder). Exported as one instance.

Logic lives here

Sorting, filtering, which tab, deciding what to fetch — the rules the View and Service must not hold.

Calls API, writes Service

Uses the apiViewController with onSuccess/onError, then pushes results into the Service via setters.

Rule: no JSX in here, and it never renders — it only decides and writes.
aqx-core · react-reservice

react-reservice in practice

The library gives us one primitive; everything else — Model, Service, ViewController, Hook — is convention we layer on top. It is what makes our MVVM fit React.

What it is

A Service class holding a plain-object context, plus useService(service, selector) — a hook that subscribes a component to a selected slice of that context.

Why it fits MVVM

Global context and state without prop-drilling, and it enforces the layer split: Service is state, ViewController is logic, Hook is subscription — a component never mutates context except through a ViewController.

Rule of thumb: subscribe to a slice. A component re-renders only when its selected slice changes — so a single price tick re-renders only the affected rows, not the whole tree.

React Native · why

Why React Native?

Native the hard way is two codebases. React Native is one — driving real native views, not a webview.

Native, the hard way

Android in Kotlin / Java, iOS in Swift / Obj-C — two codebases, two skill sets, two teams to keep in sync.

React Native

Write JS / TS once. It drives real native views on both platforms — not a webview — so you get native-like performance from one shared codebase.

Mental model: React is the brain; the render target is swappable. Components, props, hooks, state, our MVVM — all identical. What changes: no DOM, no HTML, no CSS files.
React Native · dependencies

Two layers, two kinds of dependency

An RN app is two things stacked — a native shell with your JS bundle running inside it. Dependencies split the same way.

JS-level deps

Pure JavaScript — lodash, dayjs.

pnpm install → reload. Done.

Native deps

Ship real Swift / Kotlin — mmkv, reanimated, camera.

pnpm install → pod install → rebuild the shell & run.

Gotcha: the tell — if reloading the JS doesn't pick up a new package, it's a native dep. The JS bundle is the face you can hot-swap; the native shell is the body you have to recompile.
React Native · web

React Native Web & the two builds

One component tree, three platforms — the bundler swaps react-native for react-native-web in the web build.

One codebase, three targets

iOS & Android via React Native · Web via react-native-web, which re-implements View/Text on HTML + CSS.

Mental model: React is the brain; the render target is swappable. react-dom draws a browser, RN draws native views, react-native-web lets RN code draw a browser too.
the .web / .native file split
// bundler picks the right file per target
Chart.web.tsx     // browser build
Chart.native.tsx  // iOS + Android
Chart.ios.tsx     // iOS only, if it differs

// or branch inline:
import { Platform } from 'react-native';
if (Platform.OS === 'web') { /* … */ }
Gotcha — two builds: a running RN app = a native shell (Xcode/Gradle, slow) + a JS bundle (Metro, instant). Saving TSX only needs Metro; a new native dependency needs a shell rebuild. Know which one broke.

Mobile UI · safe areas

SafeAreaView — stay out of the hardware

A phone screen isn't a clean rectangle. Draw edge-to-edge and the notch, status bar, or home indicator clips your UI.

Wrap each screen

Use SafeAreaView from react-native-safe-area-context so padding adapts per device and orientation.

Read real insets

useSafeAreaInsets() gives you the actual top/bottom values when you need finer control.

OrderScreen.tsx
import { SafeAreaView }
  from 'react-native-safe-area-context';

function OrderScreen() {
  return (
    <SafeAreaView style={{ flex: 1 }}>
      {/* your UI — never clipped */}
      <OrderTicket />
    </SafeAreaView>
  );
}
Gotcha: never hard-code paddingTop: 44 — the inset differs per device and per orientation. Let SafeAreaView read the real insets for you.
Mobile UI · running it

Mobile UI · release model

Expo, EAS Update, and why we're "bare"

Two ways to ship a change — one takes minutes, one takes days.

JS-only change → OTA

Bug fix, copy, layout tweak. eas update ships over-the-air — users get it on next launch, no store review.

Native change → store

New native dep, permission, SDK bump. gradlew / xcodebuild + review — days, and a version bump.

Mental model: we're bare RN — we own the ios/ and android/ folders ourselves, while using Expo's native modules (expo-updates, splash-screen, vector-icons). Full native control, Expo's batteries.
Gotcha: OTA ships JS only. Anything that touches native code still needs a full store release. JS fix → eas update; native change → apk/aab/ipa.

Stack · packages

What is an npm package?

A package is reusable code — a third-party library someone already wrote, tested and published — so we don't reinvent the wheel. Add one command, import it, build on top.

What we get from packages

React, React Query, Zod — almost our whole stack is packages. Validation, HTTP, charts, dates: pull in a proven one instead of writing it. They live on the registry (npmjs.com) and land in node_modules.

When to write it yourself

Reach for a package on solved, generic problems. Write your own when it's core to our product or trivially small.

Gotcha: every package is code you trust and ship to users — it adds weight and a maintenance/security surface. Prefer well-maintained, widely-used ones.
Stack · manifest & lockfile

Packages, manifest, lockfile

Three files orchestrate every dependency.

package.json

The manifest — dependencies (version ranges) + named scripts (dev build test). ✅ committed.

pnpm-lock.yaml

The exact resolved version of every package, so everyone installs identical code. ✅ committed · never hand-edited.

node_modules/

Where packages physically land. Huge. ❌ never committed.

Add a dep: pnpm add axios → pinned in the lockfile → lands in node_modules → import in your file.

Stack · bundlers

Bundlers — transform, bundle, serve

Our source — TS, JSX, hundreds of files — isn't something a browser can run. A bundler does three jobs.

Transform

Compile TypeScript and JSX into plain JavaScript; process styles and images.

Bundle

Follow every import from the entry file, merge the graph, tree-shake unused code.

Serve (dev)

A dev server with HMR: save a file and the changed module swaps into the running page in ~100ms, keeping state.

Two commands: pnpm dev → dev server + instant HMR · pnpm build → dist/ of optimized static files → deploy to CDN.
